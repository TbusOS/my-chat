Long Context 长上下文直接塞
不检索，直接把所有文档塞进上下文窗口
代表产品
Claude Opus 4.6 — 1M tokens Gemini 3.1 Pro — 2M tokens GPT-5.4 — 1M tokens
为什么 Claude "摒弃" RAG

1M tokens 约等于 2000 页文档。对于大多数企业内部知识库场景，直接塞入上下文窗口就够了，无需构建复杂的检索管道。完整上下文让模型获得全局理解能力，而不是只看片段。

优点
  • 无需检索 pipeline，架构极简
  • 完整上下文理解，无语义断裂
  • 多跳推理自然流畅
  • 部署和维护成本低
缺点
  • 按 token 计费，成本高
  • 有上限，塞不下 TB 级数据
  • "大海捞针"问题 — 信息可能被淹没
  • 首次请求延迟较高
适用场景

文档量 < 2000 页、需要深度理解全文、多跳推理、不想维护 RAG 基础设施

🕸️
GraphRAG 图谱增强检索
用知识图谱增强检索，解决多跳推理难题
代表产品
Microsoft GraphRAG Neo4j + LLM
工作原理

先用 LLM 从文档中提取实体和关系，构建知识图谱（如：张三 -[就职于]- A公司 -[总部在]- 北京），然后在图谱上检索，支持沿关系链多步推理。

优点
  • 解决多跳推理问题
  • 结构化知识表示
  • 全局理解能力强
  • 支持因果链推理
缺点
  • 构建图谱成本极高
  • 维护和更新复杂
  • 小数据集不划算
  • 图谱抽取可能有误
适用场景

大规模企业知识库、法律/医疗等需要推理链的场景、需要全局摘要的分析任务

⚡
Cache / KV-Cache 缓存方案
缓存长文档的计算结果，后续请求复用
代表产品
Claude Prompt Caching Gemini Context Caching
工作原理

把常用的长文档缓存为 KV-Cache（注意力计算的键值对），后续请求时直接复用缓存结果，不需要重新计算。相当于"预热"模型对文档的理解。

优点
  • 后续请求延迟降低 80-90%
  • 成本大幅降低
  • 与 Long Context 完美配合
  • 无需额外基础设施
缺点
  • 首次"塞入"仍需完整成本
  • 缓存有时间限制（通常几小时）
  • 缓存失效需重建
  • 仍受上下文窗口限制
适用场景

反复查询同一组文档、客服/FAQ 场景、文档相对稳定不常变的场景

🧬
Fine-tuning 微调
把知识直接训练进模型权重
工作原理

在预训练模型基础上，用特定领域的数据继续训练，将知识"刻"进模型的神经网络权重中。模型内化了知识，不需要外部检索就能回答。

优点
  • 无需检索，响应最快
  • 回答风格一致
  • 推理时无额外开销
  • 适合特定领域术语
缺点
  • 训练成本高（GPU 资源）
  • 知识过时需要重新训练
  • 可能遗忘原有能力
  • 不能引用来源
适用场景

知识稳定不常变、需要特定回答风格、对延迟要求极高、对回答格式有严格要求

🤖
Agentic RAG 智能体检索
Agent 自主决定是否检索、检索什么、检索几次
工作原理

不再由固定管道决定检索流程，而是让 Agent 像人类一样思考：先判断是否需要检索，再决定用什么关键词搜索，检索后评估结果质量，不满意就换个角度再搜。可以结合多个数据源和工具。

优点
  • 智能检索策略，按需检索
  • 可多轮检索，逐步深入
  • 可结合搜索引擎、数据库等多种工具
  • 复杂问题处理能力强
缺点
  • Agent 决策可能出错
  • 架构更复杂
  • 响应更慢（多轮调用）
  • 成本更高（多次 LLM 调用）
适用场景

复杂问答需要多步检索和推理、跨多个数据源查询、需要动态调整策略的场景

2023

RAG 是唯一选择

  • 上下文窗口只有 4K-32K tokens
  • GPT-3.5 仅 4K，GPT-4 最大 32K
  • 想让模型使用私有数据？必须 RAG
  • LangChain / LlamaIndex 爆发式增长
2024

Long Context 开始挑战 RAG

  • Claude 3 突破 200K tokens
  • Gemini 1.5 Pro 达到 1M tokens
  • 中小数据场景不再需要 RAG
  • GraphRAG 概念兴起，Microsoft 开源
2025

RAG 不再是必需

  • Claude / GPT 达到 1M+ tokens
  • Gemini 达到 2M tokens
  • Prompt Caching 大幅降低 Long Context 成本
  • Agentic RAG 开始替代传统 RAG 管道
  • 但大规模数据（10万+页）仍然需要 RAG
2026

混合方案成为主流

  • 小数据 → Long Context + Cache
  • 大数据 → RAG + Agentic
  • 企业级 → GraphRAG + Agentic RAG
  • 各方案按场景各就各位，不再"一招鲜"

📖 术语表 Glossary

RAG
Retrieval-Augmented Generation — 检索增强生成，先从数据库检索相关文档，再让 LLM 基于检索结果回答
Embedding
向量嵌入 — 将文本转换为数学向量（一串数字），使计算机能衡量文本之间的语义相似度
Vector Database
向量数据库 — 专门存储和检索向量的数据库，如 Pinecone、Milvus、ChromaDB、Qdrant
Chunk
文档切片 — 将长文档切分成 500-1000 token 的小片段，便于精确检索
Top-K
检索最相关的 K 个文档片段（K 通常为 3-10），送给 LLM 作为上下文
Reranker
重排序器 — 对初步检索结果用更精确的模型二次排序，显著提高准确率
Long Context
长上下文 — 直接把大量文本塞进模型的上下文窗口，不经过检索。1M tokens 约等于 2000 页
GraphRAG
图谱增强检索 — 先从文档中抽取实体和关系构建知识图谱，然后在图谱上检索，支持多跳推理
KV-Cache
缓存 Transformer 注意力计算的键（Key）值（Value）对，后续请求直接复用，避免重复计算
Prompt Caching
API 层面缓存长 prompt 的计算结果，后续相同前缀的请求可复用，降低成本和延迟 80-90%
Agentic RAG
Agent 自主决定检索策略的智能 RAG — 是否检索、搜什么、搜几次，都由 Agent 动态决定
Fine-tuning
微调 — 在预训练模型基础上用特定数据继续训练，将知识直接"刻"进模型权重
多跳推理
Multi-hop Reasoning — 需要多步检索和推理才能回答的问题，如"A公司CEO的母校在哪个城市？"
Cosine Similarity
余弦相似度 — 衡量两个向量方向接近程度的指标，值为 -1 到 1，1 表示方向完全一致
